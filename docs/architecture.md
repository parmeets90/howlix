# Architecture

## Milestone 2 overview

Howlix uses a deliberately small local architecture that fits an 8 GB Windows development laptop.

```text
Browser (Next.js :3000)
  |                    |
  | control/status     | signed multipart PUT requests
  v                    v
FastAPI (:8000)    private Cloudflare R2 bucket
  |                    ^
  v                    | download / delete / signed preview
Supabase Postgres  <- local FFprobe worker
```

The frontend and backend are independent applications. The browser reads `NEXT_PUBLIC_API_URL` and calls the versioned `/api/v1` API for project, upload-session, signing, completion, and status operations. Video bytes travel directly between the browser and R2; they never pass through FastAPI or PostgreSQL. The backend alone receives the Supabase and R2 credentials. Alembic owns database schema changes.

## Frontend

- Next.js App Router and TypeScript
- Tailwind CSS with reusable shadcn-style primitives
- Lucide icons
- Client-side project reads and writes with explicit loading, empty, and error states
- A direct multipart uploader using 16 MiB slices, at most two concurrent XHR requests, and true byte progress
- Local recovery metadata that stores no credentials or signed URLs; the user must reselect the same browser file after refresh
- Project detail polling for persisted media and worker status

`frontend/lib/api.ts` is the frontend API boundary. Keeping calls in one module makes it straightforward to add authentication headers, generated clients, or request tracing later.

## Backend

- `app/main.py`: application factory, middleware, health endpoint, and router registration
- `app/api/`: versioned HTTP route handlers
- `app/models.py`: SQLAlchemy domain models
- `app/schemas.py`: Pydantic request and response contracts
- `app/database.py`: engine, session factory, and request-scoped database dependency
- `app/errors.py`: consistent error envelopes
- `app/services/storage.py`: private R2 S3-compatible operations and presigning
- `app/services/media_probe.py`: strict FFprobe subprocess and metadata parsing boundary
- `app/worker.py`: PostgreSQL-claimed validation jobs, leases, retries, and expired-upload cleanup
- `alembic/`: reviewed schema migrations

The project API is synchronous by design. The initial traffic profile does not benefit from an async database stack, and SQLAlchemy's small connection pool keeps the implementation and laptop resource use modest. The engine uses connection pre-ping, a three-connection base pool, and encrypted Supabase connections configured by URI.

## Data model

Milestone 2 preserves `Project` and adds:

- `MediaAsset`: sanitized original filename, private R2 key/bucket, declared size/type, verified media metadata, and validation status
- `UploadSession`: R2 upload ID, exact part size and expected size, lifecycle state, and expiry
- `ProcessingJob`: durable validation job, attempt limits, lease ownership, failure details, and timestamps

Object keys are generated by the backend as `projects/{project_uuid}/originals/{asset_uuid}.{extension}`. Browser requests never choose a bucket, key, or R2 upload ID.

## Storage boundary

The relational database lives in Supabase. Original videos live only in the private Cloudflare R2 bucket. The worker downloads one object at a time into a system-controlled temporary directory and removes it in a `finally`-equivalent context cleanup. `storage/` remains ignored and is not durable media storage.

## Security boundary

This milestone is for one developer on localhost. It has no accounts or authorization and is not safe for public access. CORS is limited to `http://localhost:3000`; upload creation and URL signing have a lightweight in-process rate limiter; per-file and per-project quotas are enforced; signed URLs expire quickly; and actual media type is verified by FFprobe rather than trusting the browser MIME type. Distributed rate limiting must replace the local limiter before a multi-instance deployment.

The database password and R2 API credentials stay in root `.env` and are used only by FastAPI/Alembic/the worker. Presigned URLs are temporary bearer tokens scoped to one operation, object key, upload ID, and part number.

Automated tests deliberately use a temporary SQLite database. This keeps the suite fast, deterministic, and free of cloud writes; application runtime and migrations target Supabase Postgres.

## Future service boundaries

Transcription, moment analysis, and clip rendering remain future services behind the persisted job boundary. The worker is intentionally sequential for the 8 GB development machine. A production multi-user deployment will also need authentication, authorization on every project/media operation, distributed rate limiting, observability, and a managed worker runtime.
